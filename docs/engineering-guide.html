SpendBoard Engineering Guide

A complete walkthrough of how SpendBoard works: every component, every rule for versioning and publishing, how data sources and filters are wired, how queries are cached and run at scale, where files live, how the platform reports its own health, how the dashboard assistant answers questions, and how the demo recorder works. Written to be read start to finish.

Architecture diagrams

01How to read this

SpendBoard is a platform for building chart cards (a KPI, a bar list, a trend line), placing them on dashboards, and reusing the same card on many dashboards. Each card reads from a data source: a Postgres database, a BigQuery dataset, a REST API, or an uploaded CSV, Excel or JSON file.

On top of that sit four big ideas, and the chapters follow them in order:

  1. Governance. Everything is versioned, lives in a private space or the global library, and gets into the global library only through an admin-reviewed change request that merges like a pull request (chapters 4–9).
  2. Data sources and a semantic layer. Sources are described in business terms (dimensions, measures, a time dimension), and cards and filters work in those terms (chapters 10–13).
  3. Scale. Card results are cached and shared, queries run on workers with per-source limits, and a dashboard loads in one streamed request (chapter 14).
  4. The assistant. A chat panel answers questions about the dashboard on screen, using tools rather than raw data (chapter 15).

Operations run through several chapters: file storage on disk or S3 (chapter 10), protection against hung sources and long-running queries (chapter 14), the frontend's data layer and the demo recorder (chapter 16), and health checks (chapter 18).

Each chapter explains what happens, then why it was designed that way (in blue boxes), then the exact rules and settings. Code locations are given as paths in the repository, e.g. backend/app/governance/service.py.

Two paths

Everything in the system follows one of two paths.

The request path is browser → web server → API → Postgres/Redis. It handles reading and saving definitions, permissions, and looking up cached card results. It never connects to a data source.

The execution path is Redis queue → worker → data source → Redis. When a card result isn't cached, the API puts one job on the queue; a worker runs it against the source, writes the result into the cache, and announces it is done. The API then streams the result back to the browser.

Why split them

Data sources can be slow or flaky, and dashboards are viewed by many people at once. Keeping source queries off the request path means a slow source can never tie up the API, the number of queries hitting a source can be capped across the whole cluster, and identical requests from many viewers turn into one query.

03Sign-in and identity

SpendBoard behaves as if a corporate single-sign-on provider stood in front of it. In this build the web server plays that provider, so the same code will work with Okta or Azure AD later by changing configuration only.

  1. The sign-in page lists directory users from GET /auth/users (Avery Admin, Riley Analyst, Jordan Analyst).
  2. Choosing one calls POST /auth/token. The web server signs a JWT with an RSA key (RS256). Claims: sub (user id), email, name, roles, iss = spendboard-auth, aud = spendboard-api, exp one hour later. The signing key is generated once and kept in apps/web/server/.keys/ so tokens survive restarts.
  3. The SPA stores the token in sessionStorage (per browser tab) and sends it on every API call as Authorization: Bearer <token>. A 401 response signs the user out.
  4. FastAPI reads the token's key id, fetches the public keys from /auth/.well-known/jwks.json (cached for ten minutes, refetched immediately if an unknown key id appears, which handles key rotation), and verifies signature, issuer, audience and expiry.
  5. The user row is created on first sight (just-in-time provisioning) and its name, email and role are updated from the token on later requests. The role is admin if the token's roles include it, otherwise user.

Because people should be findable for sharing before they ever sign in, the seed script also pre-creates the three directory users. In production that role is played by directory sync (SCIM) from the identity provider.

Why JWT + JWKS

It is how real OIDC providers work. The API never shares a secret with the identity provider; it only needs the provider's public keys. Switching to a real provider means pointing JWKS_URL, JWT_ISSUER and JWT_AUDIENCE at it and mapping its role claim.

In production

The hosting platform signs users in, so the simulated provider is development-only. Connecting to the platform is configuration: set JWKS_URL, JWT_ISSUER and JWT_AUDIENCE, and check how its token marks admins. The backend treats a user as admin when the token's roles list contains "admin" (backend/app/core/auth.py); a different claim name (groups, role, a group id) is a one-line change. Without it, everyone signs in as a normal user.

Code: apps/web/server/index.mjs, backend/app/core/auth.py, apps/web/src/lib/auth.ts.

Database-level guarantees

  • A trigger (asset_versions_immutable) raises an error on any UPDATE or DELETE of a version row.
  • Check constraints restrict kind, scope, role, share permission, request status and item type to their allowed values.
  • A private asset must have an owner; global assets have none (they belong to the organisation).
  • assets and asset_versions reference each other (head version, fork base); those two foreign keys are added after both tables exist.

The analytics data itself is not in this database. The demo data lives in a separate demo_warehouse database (60,000 card transactions, generated by a deterministic random generator so it is identical on every machine) and is queried through a read-only role, exactly like any customer database would be.

05Versioning

Cards, dashboards and data sources are versioned the same way, by the same code (backend/app/governance/service.py).

Assets and versions

An asset is the thing you'd name in conversation: "the Product Spend card". It has an owner, a scope, and a pointer to its current head version. A version is a full snapshot of the asset at one save: its name, description and complete typed spec. Saving never edits; it always appends version n+1 and moves the head.

Why immutable versions

Three later features depend on it. Dashboards can point at an exact card version and keep rendering it unchanged. Change requests can compare "what you started from" with "what you propose". And cached results can be keyed by version id, because a version's definition can never change underneath the cache.

What happens on save

  1. Validate the spec against the kind's schema (Pydantic). Unknown fields are rejected.
  2. Check references. Every version the spec points at must exist, belong to the named asset, be of the right kind (cards point at data sources, dashboards at cards) and be visible to the saver. A global asset may never point at a private one — that would leak private work into the shared library — so this returns 409 "publish it first".
  3. Data-source policy (data sources only): credential reuse, server-setting references, file ownership and the network guard (chapter 11).
  4. Lock the asset row (SELECT … FOR UPDATE) so two simultaneous saves can't both become "version 4".
  5. Insert the version with version_no = max + 1, record its dependency edges, move the asset's head, copy name and description onto the asset for fast listing, update updated_at, and write an audit event.

Pinning

References always name a version, not just an asset: a dashboard placement says "card 7, version 12"; a card says "data source 1, version 3". This is called pinning.

  • Editing a card creates a new card version but does not change any dashboard. The dashboard keeps rendering the version it pinned.
  • When a pinned card has a newer head, the dashboard shows an Update chip on that card and a banner listing them. Update all (POST /dashboards/:id/apply-updates) re-pins those placements to the latest versions and saves that as a new dashboard version.
  • When a card is saved, it pins the current head of its data source.
  • Laying out a dashboard keeps existing placements on their pins (matched by the placement's stable item_id); newly added cards are pinned to their current head.

History, comparison, restore

  • GET /:kind/:id/versions lists versions with author, time and change note.
  • GET /:kind/:id/diff?from_no=&to_no= returns a structural diff: a list of changes, each with a JSON path, an operation (added, removed, changed), the before and after values, and for multi-line text (SQL) a unified line diff. Lists of objects are matched by a stable key — item_id for dashboard placements, id for filters, name for model entries — so moving one placement shows as one change rather than a cascade. For dashboards the response also maps placement ids to card names, which the UI uses for labels like "Added “Top Airlines”".
  • POST /:kind/:id/restore/:no appends a new version containing the old content, with the change note "Restored vN". History is never rewritten. Restoring the current head is refused.

Deleting

Delete is archive: the asset gets archived_at, disappears from lists and can't be opened directly, but its versions remain. A dashboard that pinned an archived card keeps rendering it.

08Publishing workflow

The global library changes in two ways only: an admin edits a global asset directly (a new version plus an audit event), or an admin approves a change request. Code: backend/app/governance/requests.py.

Making a copy (fork)

Edit a copy on a global asset calls POST /:kind/:id/fork. It returns the user's existing private copy if they already have one; otherwise it creates a private asset whose forked_from_asset_id and forked_from_version_id record which global version it came from, and saves version 1 with the same content. The lineage is recorded before that first version is saved, because the credential rules for data sources depend on it.

Submitting

Propose changes (a copy) or Request publish (a new private asset) calls POST /change-requests with a title and description. The API:

  1. Checks the submitter owns the private asset.
  2. Builds the bundle: the asset plus every private asset it depends on, recursively (a dashboard's private cards, their private data sources), ordered dependencies first. If a private dependency belongs to someone else, the request is refused — its owner has to publish it first.
  3. Refuses if any asset in the bundle is already in an open request.
  4. Creates the request and one item per asset. A copy becomes an update_existing item (target = the global asset, base = the version it was copied from); anything else becomes publish_new. Each item records the asset's version at submit time.

Later edits to the private asset don't change the request automatically. The requester clicks Update to my latest versions (POST /change-requests/:id/update), which rebuilds the bundle from the current versions — like pushing new commits to a pull request.

Reviewing

Admins see all requests on the Approvals page (users see their own on My requests); the sidebar badge shows the pending count. The request page evaluates every item live:

  • the changes compared with the global base (or the full contents, for a new asset);
  • whether global has moved since the copy was made ("based on v1 · global is now v2");
  • whether the item merges cleanly or has conflicts (chapter 9);
  • a live preview of proposed cards (GET /change-requests/:id/items/:item/data), which lets the admin see a card they otherwise couldn't open.

Approving

Approval runs in one database transaction:

  1. Re-evaluate every item. If any has conflicts, stop with 409.
  2. Walk the items in dependency order, keeping a map from private asset to its new global version.
  3. For each item, take the merged content and rewrite references: a card that pointed at a private data source now points at that source's new global version; a dashboard's placements point at the new global cards.
  4. publish_new: create a new global asset with version 1. update_existing: append a new version to the global asset — unless nothing actually changed, in which case the existing version is reused instead of creating a duplicate.
  5. The new version's author is the requester; the change note is "<title> (request #n)". The admin is recorded as reviewer, with their comment and an audit event.
  6. The requester's private asset is re-pointed at the published version, so their next edit is proposed as an update to it.

Reject requires a comment. Withdraw is only for the requester. Both leave the private assets untouched.

Why bundle dependencies

A global asset must never point at a private one. Without bundling, a user publishing a dashboard would have to publish each private card and source separately, in the right order, and an approval could half-succeed. Bundling makes it one decision with one outcome.

What the UI shows

Every asset response includes pending_request_id and, for copies, a fork block (which global asset, which version it was based on, the current global version, and whether it's stale). The governance bar on cards, dashboards and data sources uses these to show "Edit a copy", "Copy of global … · vN", "Global is now vM — update from global", "In review · request #n", "Propose changes" or "Request publish".

09Merging

If global has changed since a copy was made, the request is merged three ways, like a pull request (backend/app/governance/merge.py):

  • base — the global version the copy was made from;
  • ours — the proposed private version;
  • theirs — the global head today.

Rules, applied recursively through the JSON

  1. If ours and theirs are equal, take it.
  2. If only one side differs from base, take that side.
  3. If both differ and both are objects, merge key by key.
  4. If both are lists of objects with a stable key (item_id, id, name), merge item by item; added items from either side are kept, items removed on one side and unchanged on the other are removed.
  5. If both are multi-line strings (SQL), merge by line hunks; hunks that don't overlap combine.
  6. Otherwise it's a conflict at that path — including "deleted on one side, edited on the other".

Example: an admin edits the global card's description while the user's copy changes its SQL. Both changes land. If both changed the description differently, that path conflicts.

Resolving conflicts

Conflicts block approval. The requester opens Update from global on their copy (GET/POST /:kind/:id/rebase). The dialog shows what changed in global since the copy and each conflicting path side by side; the user picks "Keep mine" or "Take global" for each. Applying it saves a new version of the copy with the merged content, moves the copy's base to the current global head, and updates any open request to the new version and base — so the request now merges cleanly.

10Data sources

Every source type implements the same small interface — execute, test, introspect — so nothing above it needs to know what kind of source a card uses (backend/app/connectors/).

Postgres

  • Queried in place. One asyncpg connection pool per source endpoint and process; the pool size is the source's max_concurrency.
  • Every query runs in a read-only transaction with SET LOCAL statement_timeout and through a server-side cursor that stops after 1,000 rows, so a huge result is never fully loaded.
  • Connections should use a read-only database role (the demo uses warehouse_reader).
  • Introspection lists tables and views in the public schema with columns and estimated row counts.

BigQuery

  • Queried in place, like Postgres. A source names a project, a default dataset (unqualified table names in card SQL and the model resolve against it; dataset.table also works) and an optional location.
  • Authentication: a service-account key (the JSON file, stored encrypted like any credential), or the server's own Google identity (application default credentials) — admins only, because it can reach whatever the deployment's account can. Give the service account only BigQuery Data Viewer and BigQuery Job User.
  • Cost cap: BigQuery bills per byte scanned. Every query carries maximum_bytes_billed (10 GB by default, set per source: 1–500 GB). A query that would scan more fails before it runs, at no cost, with "This query would scan more than N GB". The platform's result cache and BigQuery's own query cache both stay on, so repeated views cost nothing.
  • Filters and dates are typed named parameters (@p1 as an ARRAY<STRING>, DATE, INT64…), never text in the SQL.
  • Each job has a server-side timeout; if the client's wait runs out first, the job is cancelled. The client library's own retries (ten minutes by default) are capped at the source's timeout, and whole-job retries are off — see "Hung sources" in chapter 14.
  • Introspection lists the dataset's tables with exact row counts from table metadata (free). Nested (RECORD) and repeated columns are left out, since the builder can't use them.
  • The builder's dimension values go through the same cached, capped lookup as filter dropdowns, because on BigQuery every distinct-value query is a billed scan.
  • For development and tests, BIGQUERY_EMULATOR_HOST sends every BigQuery source to a local emulator (npm run infra:bigquery).

REST APIs

  • Not queried live by cards. Records are fetched into a DuckDB extract, and cards query the extract. The extract is re-fetched when it's older than the source's cache_ttl_s (and by a scheduled job every minute).
  • Auth: none, bearer token, API key header, or basic auth (the secret is stored encrypted).
  • Pagination: a page-number parameter, an optional page-size parameter, a maximum page count; fetching stops at a short page.
  • A dot path (e.g. data.items) says where the records are; if omitted, the root array or the only array in the root object is used. Nested objects become parent_child columns; lists become JSON text.
  • Limits: redirects are not followed, responses over 20 MB or 100,000 records are refused.
  • Each refresh writes a new extract under the key rest/<version>-<settings hash>/<timestamp>.duckdb and moves a Redis pointer (rest:extract:…) to it, so every API and worker process agrees on the current extract. A Redis lock makes one process refresh at a time across the cluster; others keep serving the previous extract meanwhile. The previous extract is kept and older ones are deleted. Keying by version and settings hash means a recycled id never reuses another source's extract.

Files

  • CSV, TSV, Excel (.xlsx) and JSON, up to 50 MB (POST /files).
  • The file is loaded once into its own DuckDB database. Every Excel sheet becomes a table. Column types are inferred; a column with mixed types becomes text.
  • Only the uploader can build a data source from a file.
  • The original and its DuckDB database are built in local scratch space, then stored under uploads/<id>.<ext> and files/<id>.duckdb.

Where files live

All file access goes through one interface, backend/app/core/storage.py (put_file, local_path, exists, delete). Code and the database only ever hold keys, so the backend is chosen by configuration:

STORAGE_BACKEND=local (default)STORAGE_BACKEND=s3
Files liveUnder STORAGE_DIR, a disk every API and worker process mountsIn S3_BUCKET under S3_PREFIX (S3, MinIO, Cloudflare R2…)

DuckDB still needs a local file — it runs with external access disabled, so it can't read S3 itself — and local_path(key) gives it one. Keys are write-once: a new version of something is a new key, never an overwrite. That is why a cached copy can never be stale and workers need no coordination.

Moving an install to S3: migration 0004 has already rewritten older absolute paths into keys; copy the uploads/ and files/ folders into the bucket under the prefix; set STORAGE_BACKEND=s3 and the S3_* settings everywhere; restart. REST extracts rebuild themselves on first use. The tests run uploads and REST extracts against an S3 emulator (moto).

DuckDB lockdown

Queries against extracts open the DuckDB file read-only, then set enable_external_access = false and lock_configuration = true. User SQL can see only that source's tables: reading local files, exporting, attaching other databases and installing extensions all fail. DuckDB shares one in-process instance per file, so when several queries open the same file at once, later ones find the settings already locked; they verify external access is off rather than trusting the error. This was a real bug found by the concurrency tests.

Onboarding flow

  1. Pick a type (Postgres, BigQuery, REST API, file upload).
  2. Enter the connection, or upload the file.
  3. Test connection (POST /data-sources/test) returns the tables, sample records (REST), and a suggested semantic model. The password typed into the form is used only for the test and isn't stored.
  4. Edit the model (chapter 12), set the refresh interval and the query timeout (30 seconds to 5 minutes; a slow warehouse may need more than the default 30), and save as a private source. The password is now stored encrypted.
  5. Request publish, like any other asset.

The suggested model hides id and numeric *_id columns, makes the first date/time column the time dimension and records whether it is a DATE, DATETIME or TIMESTAMP, makes numeric columns summed measures (except names like year, vintage, month, code), makes everything else a dimension, and always adds a row-count measure.

The card builder's catalog comes from GET /datasets: for each visible source, its tables, model, and the distinct values of its dimensions, cached for five minutes per source version.

11Credentials and source safety

How credentials are stored

Passwords, tokens and API keys are encrypted with Fernet (derived from SECRET_KEY) into the secrets table. Specs only ever contain a reference, sec:<id>. The plaintext is decrypted inside the connector when connecting (cached in memory for 60 seconds) and is never returned by the API or written into a version. When editing a source, leaving the password field blank keeps the stored credential; clients can't set references themselves — the server ignores any they send.

Two other reference forms exist: env:NAME reads a server setting (used by the demo source so its host works both on a laptop and in Docker), and tmp:<id> holds a password typed into the test form for the duration of one test.

Rules checked on every data-source save

These run inside save_version, so they apply whether the version comes from an edit, a restore, an update-from-global or an approval (backend/app/connectors/policy.py).

12Semantic layer

The semantic model is the business vocabulary of a data source. It's stored in each data-source version, so changing it is versioned and reviewed like anything else.

dataset     transactions — "Charge transactions" — one row per card charge

Semantic cards

The card builder saves a semantic query rather than SQL:

{ "mode": "semantic", "dataset": "transactions",
  "measures":   [{"name": "total_spend"}],                 // or {"agg": "SUM", "column": "amount"}
  "dimensions": [{"name": "txn_date", "grain": "month"}],  // up to two
  "filters":    [{"dimension": "product", "values": ["Gold"]}],
  "order": "label_asc", "limit": 12 }

The compiler (backend/app/semantic/query.py) turns it into SQL for the source's dialect on every run:

  • Dimensions become label (and sublabel for a second one). Time grains: day, week, month, quarter, year — to_char on Postgres, strftime on DuckDB.
  • One measure is named value (KPIs, year-over-year and charts rely on that); several keep their labels.
  • Model measure expressions are parsed with SQLGlot and must be plain aggregates — no subqueries, no writes, at least one aggregate function. A measure such as (SELECT 1) is rejected when used.
  • Unknown datasets, measures or dimensions, and a time grain on a non-time dimension, are rejected when the card is saved (422).
  • Default order: by label for time series, by value descending otherwise.

Raw-SQL cards

Power users can still write SQL. SQLGlot parses it and allows exactly one read-only statement: SELECT, WITH, UNION are fine; anything that writes, SELECT … INTO, COPY, ATTACH, PRAGMA, SET, BigQuery's EXPORT DATA (writes to Cloud Storage), scripts (DECLARE, temporary functions), data-modifying CTEs and multiple statements are rejected. Semicolons inside string literals are fine (the original prototype rejected them). Query parameters of any style ($1, @name, ?) are reserved for filters.

Where dashboard filters should apply, the SQL contains a {{filters}} marker, e.g. WHERE 1=1 {{filters}}. It is replaced with conditions bound as parameters, using the model of whichever modelled table the SQL reads from.

View SQL on a semantic card, and Open in SQL editor from the builder, show an editable form: static filters as safely quoted literals, plus the {{filters}} marker, so it runs unchanged as a raw SQL card.

Why a semantic layer

It does three jobs with one definition: the builder offers "Total spend by Merchant" instead of column names; dashboard filters can bind by meaning across different sources; and the assistant can reason about and query data by business names, through a compiler that only produces bounded, read-only, aggregated SQL.

13Filters

How a filter reaches SQL

A filter value travels as business terms: {"segment": ["GCS"], "sub_segment": ["SBS", "MM"]} plus a date window. Each card binds it through its own source's model (backend/app/semantic/filters.py):

  • a dimension the dataset has becomes a list-membership condition in the source's dialect (see chapter 12) — values always bound as parameters;
  • the date window binds to the dataset's time dimension. For a DATE column the window is inclusive (>= from AND <= to). For DATETIME and TIMESTAMP columns it runs to the start of the day after to (< to + 1 day), so the whole last day counts, and on BigQuery the bound is converted to the column's type, since BigQuery won't compare a TIMESTAMP with a DATE;
  • anything the dataset can't bind is reported, not dropped. Every card result carries meta.applied and meta.ignored.

A card with ignored filters shows a Partly filtered chip whose tooltip names the filters and why. Year-over-year figures are only computed when the period actually applied.

Dashboard filter definitions

Each dashboard has its own filters, edited in edit mode under Filters and saved as a new version (PUT /dashboards/:id/filters):

FieldMeaning
dimensionThe business dimension it filters, e.g. segment
kindselect (one value), multi (several), or period (date window)
parentAnother filter that narrows this one's options (Segment → Sub-segment)
lockedCards may not override it
defaultInitial value; for the period, a preset such as ytd
source_idOptional: which source supplies the options (default: the first card source whose model has the dimension)

The editor's dimension list comes from GET /dashboards/:id/filterable, which gathers dimensions across all the dashboard's card sources and notes when several sources share one.

Cascading options

A dropdown's options come from GET /dashboards/:id/filter-options/:filter?selections=: the distinct values of the dimension, narrowed by the current selection of every ancestor. With Segment = GCS, Sub-segment offers only G&L, MM and SBS. Changing a parent clears all of its descendants. Options are cached for five minutes per source version and selection.

Card-level overrides

A card can expose its own filter dropdowns for any dimension of its source (configured in Card Studio under "Filter dropdowns on the card", plus an optional period dropdown). The effective value for a card is:

  1. the card's own dropdown — if the card shows that dimension and the dashboard filter isn't locked;
  2. otherwise the dashboard's selection;
  3. otherwise the filter's default;
  4. otherwise no filter.

Card overrides reset whenever the dashboard filters change. On the card, later dropdowns narrow to earlier ones, mirroring the dashboard's parent rule. Options come from GET /cards/:id/filter-options.

Period presets

ytd (2026-01-01 to 2026-06-11, matching the demo data), all, months, quarters ("Q1 '26") and full years ("FY '25"). The frontend and the warm-up job share the same definitions (PeriodSelect.tsx, backend/app/semantic/periods.py).

14Running queries at scale

This chapter follows one dashboard load end to end. Code: backend/app/execution/jobs.py, backend/app/api/dashboards.py (render), apps/web/src/lib/render.ts.

1 — One request per dashboard

Each card on the page asks a shared render batcher for its data, with its effective filters. The batcher collects every request made within 25 ms and sends one POST /dashboards/:id/render with all of them. The response is a stream of server-sent events: an event: card for each card as soon as it's ready, then event: done. Cards resolve one by one, so cached cards paint immediately while the rest compute.

The API checks that each requested placement is on the dashboard, loads the pinned card and source versions in two queries, and starts all the lookups concurrently.

2 — The cache lookup

Each card becomes a job carrying everything a worker needs: the card version id and spec, the source version id and spec, and the filters. Its cache key is:

res:<card_version_id>:<source_version_id>:<hash of canonical filters>

Because both ids are immutable versions, a cached entry can only ever belong to exactly that definition. Because every user sees the same rows, one entry serves everyone.

Lookup resultWhat happens
Fresh hit (before fresh_until)Returned immediately.
Stale hit (past the TTL, within 6 h grace)Returned immediately, marked stale; a refresh is triggered in the background. The card shows "Refreshing · as of …" and checks again after 2.5 s (up to three times).
MissSingle-flight: see below.

3 — Single-flight

On a miss the API first subscribes to the key's completion channel, then tries SET lock:<key> NX. Whoever gets the lock dispatches the job; everyone else just waits on the channel. When 500 people open the same uncached view at the same moment, the source sees one query.

  • The lock expires after the source's query timeout plus 20 seconds. The queued job expires at the same moment: if no worker has started it by then, its waiters have already re-dispatched it or given up, so it is dropped instead of piling up.
  • Waiters wait as long as the query may legitimately run: the source's timeout plus 25 seconds, and never less than RESULT_WAIT_S (60 s). If a waiter sees the lock disappear without a result — the worker crashed or the message was lost — it takes over and dispatches the job itself.
  • If the job fails, its error is stored for 30 seconds and every waiter receives it.

4 — The worker

  1. A Celery worker takes the job from the interactive queue. Each worker process keeps one event loop for its whole life, so database pools and the Redis client are reused across jobs.
  2. If the source's circuit breaker is open, fail fast.
  3. Take a source slot: a Redis counter per source endpoint, capped at the source's max_concurrency across all workers. If no slot frees up in time, fail with "the data source is busy".
  4. Run the card: compile the query, bind the filters, execute. If a full date window applied, run the same query one year earlier for year-over-year figures (a single delta for KPIs, per-row deltas otherwise). The whole run has a hard deadline of the source's timeout plus 10 seconds, whatever the connector.
  5. Write the result with fresh_until = now + cache_ttl_s, expiring after TTL + 6 h; record the compute time; release the lock; publish "done".

Failures that come from the source count towards the breaker: five within a minute opens it for 30 seconds. Compile and validation errors don't count against the source.

5 — Scheduled work (Celery beat)

  • Every 60 s, on the refresh queue: re-fetch REST extracts that are past their TTL.
  • Every 5 min: warm-up — for each global dashboard, trigger every card at the dashboard's default filters, so the first viewer finds them cached.

The separate refresh queue means scheduled work never delays interactive dashboard loads. Each scheduled run expires with its interval: if the workers are busy, a round is skipped rather than queued behind the others.

6 — Hung sources

On 5 October 2026 a BigQuery endpoint became unreachable in development. Google's client library retries failed calls for up to ten minutes by default, and wraps job submission in a private ten-minute retry of its own. Every worker process sat retrying, so cards on every other source queued behind them and timed out after 60 seconds, while waiting requests kept queueing fresh copies — 272 jobs in all. Nothing failed, so the circuit breaker never opened.

Four layers now stop one dead source from taking every worker:

LayerWhereEffect
Bounded client retriesconnectors/bigquery.pyAPI calls retry only within the source's timeout; whole-job retries off
Job deadlineexecution/jobs.pyAny card run ends at the source's timeout + 10 s, so failures reach the breaker
Task time limitsworker/celery_app.pyCard tasks: soft limit QUERY_TIMEOUT_S + 60 s, hard + 90 s (the process is replaced)
Expiring jobsexecution/queue.py, beat scheduleJobs nobody waits for anymore are dropped instead of building a backlog

With these in place, stopping the emulator on purpose gave: BigQuery cards failed within their 30-second timeout, the breaker paused the source after five failures, and a Postgres card answered in 0.07 seconds throughout.

7 — Long-running queries

A warehouse query may legitimately take minutes. Each source sets its timeout in its editor (30 seconds by default, up to 5 minutes); QUERY_TIMEOUT_S (default 300) is only a server-wide ceiling. Everything else derives from the source's timeout: the job deadline (+10 s), the single-flight lock (+20 s), how long viewers wait (+25 s), the BigQuery retry budget, and how long a per-source slot counter lives, so a long query can't let the concurrency cap reset mid-query. A proxy in front of the app must allow requests that long too (the INSTALL guide's nginx example uses 330 s).

8 — The queue is swappable

Work is handed to a queue in exactly one place, backend/app/execution/queue.py: submit(task, payload, queue, expires_s) on the producer side and handle(task, payload) on the consumer side. A job is a self-contained JSON payload and duplicates are harmless (they recompute the same cache entry), so any at-least-once queue works.

OptionChangeVerdict
Celery on Redis—Current; right for this workload
Celery on RabbitMQ or SQSCELERY_BROKER_URL=amqp://… or sqs://…The easy upgrade to a dedicated broker
Redis Streams / SQS with a small asyncio consumerA new backend in queue.py plus a consumer calling handle()Fewer moving parts, if Celery ever becomes a burden
KafkaAs aboveNot for this job queue
Why not Kafka for the jobs

A dashboard view fans out about ten queries that must start within milliseconds; some take 50 ms, some minutes, and any free worker should take the next. That is a work queue. Kafka is a log: work is pinned to partitions, so one slow query blocks everything behind it, consumers are capped by partition count, and there are no per-message retries or priorities. It would fit alongside the queue, as a stream of events such as "version published" or "request approved" for other systems.

Measured baseline

Everything ran on one laptop. In the mixed run, 167,000 card lookups needed 1,007 queries; the latency came from CPU contention (even the uncached "dashboard detail" call had the same median). In the cold run queries took ~15 ms; the rest was waiting for one of eight worker processes. Run it yourself with the commands in docs/loadtest.md.

Why Celery and Redis

Redis already had to exist for the cache; using it as the broker, the lock service and the completion channel keeps the moving parts to one. Celery adds dependable delivery (acknowledge-after-completion, so a crashed worker's job is redelivered), separate queues and a scheduler. Its limit is one job per prefork process, which matters only for cold, I/O-heavy traffic (chapter 20).

15Dashboard assistant

A chat button floats in the bottom-right of every dashboard. Code: backend/app/assistant/, backend/app/api/assistant.py, apps/web/src/components/AssistantWidget.tsx.

What it answers from

When you ask a question, the panel sends the question, the conversation so far, the current filter summary ("Segment: GCS · 2026 YTD") and every card with its filters. The API then builds the context:

  • the dashboard's name, description and filter definitions;
  • every card as shown: name, description, chart type, what it breaks down by, which filters applied or didn't, up to 25 result rows, and year-over-year figures — fetched through the same cache as the dashboard, so it's exactly what you're looking at;
  • the semantic catalog of each source on the dashboard (datasets, dimensions, measures, with labels and descriptions), each given a short key such as s1.

The model never receives raw source rows.

Three modes

Offline (default)LLM_PROVIDER=offlineNo model calls. Rules over the context answer totals, which segment or item leads, what's growing fastest, top N, how concentrated spend is, and "what am I looking at", with filter buttons when a matching dashboard filter exists.

The tool loop

With a model configured, the API sends a system prompt, the context, the history and the question, plus four tools in OpenAI function format. The tools run on the server:

ToolDoesLimits
query_dataA semantic query (dataset, measures, dimensions, time grain, filters, dates, order) against one of the dashboard's sources, through the same compiler as cardsOnly sources used on this dashboard; ≤ 50 rows
list_dimension_valuesValid values of a dimension, with optional search≤ 100 values
get_cardRe-runs one of the dashboard's cards with other filters or dates, via the cacheOnly this dashboard's cards
suggest_filterAdds a "Filter to …" button to the answerOnly this dashboard's filters; nothing changes until the user clicks

The loop runs up to six rounds of tool calls; on the last round tools are switched off and the model must answer. Tool errors (unknown source, unknown measure, bad arguments) are returned to the model as text so it can correct itself. <think> blocks that some local models emit are removed.

What comes back

  • answer — the text;
  • sources — the cards it cited: cards named in the answer, in order, plus cards re-run with get_card. In the panel these are the "From" chips; clicking one scrolls to the card and flashes it;
  • actions — filter buttons; clicking applies the dashboard filter (and clears dependent filters);
  • tool_calls — what it ran, shown as a small "Ran 2 queries" line.

Safeguards

  • Card names, descriptions and tool results are written by users; the context is labelled as data and the system prompt says instructions inside it are to be treated as text.
  • Every tool is read-only, scoped and capped. The only effect on the page is a button the user chooses to click.
  • 20 questions per user per minute.
  • Each question is audited with its length and the tools used; the answer isn't stored.
  • Model problems (unreachable, rejected key, unknown deployment, rate limit, timeout) return a clear 503 message.
Why tools instead of sending the data

Real sources are far too large to send, and sending them would bypass permissions. Giving the model the catalog plus bounded tools means it can ask precise questions, every answer is computed by the same governed engine as the cards, and nothing it does can exceed the asking user's access.

The UI decides what to offer from fields the API sends with every asset — access, can_edit, scope, pending_request_id, fork — and the API enforces the same rules again on every call.

Server data and editing state

Almost everything on screen is server data (assets, versions, requests), and what isn't belongs to one page (filter selections, edit mode). So there is no global store such as Redux or MobX. Instead:

  • TanStack Query (lib/queries.ts) caches lists, details, versions, shares, requests, filter options and previews; shares them between components; de-duplicates requests; and refreshes in the background. Pages open instantly from cache when you come back to them.
  • Writes refresh what's on screen. Every successful write (save, share, fork, approve, restore…) marks governance data stale, so lists, the approvals badge and "update available" update without manual reloads. Query keys starting with data — card previews, filter options, compiled SQL — are keyed by immutable versions and never invalidated by writes. Failed requests retry once, but not on 4xx errors. Signing out clears the cache.
  • The dashboard page uses a reducer (lib/dashboardEditor.ts) for its layout, edit mode and filter selections. A background refresh replaces the layout only when there are no unsaved changes, and resets filters only when the dashboard's filter definitions themselves changed.
  • The card and data-source editors fill their forms once per version and don't refetch on window focus, so a background refresh can never overwrite edits in progress; a save, restore or update from global (each a new version) refills the form.

Demo recorder

Record demo (bottom of the sidebar) captures a guided walkthrough and exports it as a single self-contained HTML reel. Code: apps/web/src/features/demo-recorder/.

  1. Starting a session shows a floating recorder bar on every page; it can be dragged and remembers its position.
  2. Capture scene uses the browser's Screen Capture API (getDisplayMedia, current tab offered first; one permission prompt per session). All recorder UI is hidden, the recorder waits for a frame painted after that, grabs it, and shows it frozen so the user can drag a region or keep the whole screen. 3 s delays the capture so a menu can be opened or hovered first. Clicks on the bar don't close the app's open menus.
  3. The scene editor sets a title and caption and holds one or more images; for each image, a click sets where the camera zooms, plus the move (zoom in, zoom out, still) and how long it shows.
  4. The scene list reorders (drag or arrows), re-captions, re-captures and deletes.
  5. Finish names the reel and offers Preview and Download. The file embeds every image as WebP or JPEG plus the player's code and styles; it needs no network.

The reel plays like a slide show: it advances on its own with a smooth zoom or pan between two camera positions (Web Animations, clamped so the image always fills its frame), shows captions, and supports Space to pause, ← → to step, Home and End, F for full screen, and a clickable progress track. A recording is kept in the browser's IndexedDB per user, so it survives navigation and reloads; nothing is uploaded.

Why screen capture rather than redrawing the page

Rendering the page from its HTML (html-to-image) needs no permission prompt, but it gets fixed elements such as the sidebar wrong once the page is scrolled, and fonts and charts come out imperfectly. Screen capture costs one prompt and gives exact pixels.

The feature is self-contained: the app imports it once (one import and one JSX line in App.tsx), it loads only when someone starts recording, and building with VITE_DEMO_RECORDER=false leaves it out of the bundle entirely.

Health checks and alerts

Card queries run on workers, so "the API answers" proves little: workers can be alive yet stuck, as on 5 October, when every process check stayed green for hours. Health is measured by progress. Each worker records every task it finishes or discards (Celery signals), and backend/app/ops/health.py builds one snapshot from Redis: Postgres and Redis reachability, queue depth, jobs in flight, how long the oldest card job has been held, seconds since the last worker progress, and open breakers.

StatusWhen
failingPostgres or Redis unreachable; or no worker progress for STUCK_AFTER_S while card jobs wait in the queue, or while a card job has been held longer than that
degradedMore than QUEUE_WARN_DEPTH jobs queued, or a data source paused by its breaker
okAnything else, including an idle system

STUCK_AFTER_S is longer than any query may run, so a slow BigQuery job is never "stuck". Refresh jobs, which may legitimately run long, are never counted. A freshly restarted worker reports healthy at once: it records progress when it starts, even while the broker still lists jobs its stuck predecessor held (those are released after the visibility timeout, QUERY_TIMEOUT_S + 120 s, instead of Celery's default hour).

GET /readyz on the APIAPI readiness probePostgres or Redis unreachable
python -m app.ops.check in the worker containerWorker liveness probe — the platform restarts stuck workersWorkers stuck (exit code 1)

Why stuck workers don't fail readiness

If they did, the platform would take every API replica out of service, turning "uncached cards fail" into "the whole app is down". Stuck workers trigger a worker restart and an alert instead. The check is cluster-wide on purpose: if card jobs wait and no worker anywhere progresses, any healthy worker would have taken them, so every worker is stuck.

Metrics include spendboard_status (0 ok, 1 degraded, 2 failing), spendboard_workers_stuck, spendboard_queue_depth, spendboard_jobs_in_flight, spendboard_seconds_since_worker_activity, spendboard_breakers_open, cache lookups, computations and latency. Suggested alerts: status 2 for two minutes; status 1 for ten; a breaker open for ten. Probe endpoints sit outside /api, so the web server never exposes them. Verified by freezing the dev worker's eight processes: the check failed with both reasons while /readyz stayed ready, and after a forced restart it passed at once.

Seeding and upgrades

That step works through normal versioning: the demo source gets a version with the full semantic model, global cards are re-pinned to it as new versions, and the demo dashboard gets a version with its filters and updated pins.

20Open items and glossary

Open items

  • Assistant with a real model. Built and tested against a scripted OpenAI-compatible server; configure Ollama or Azure to try it end to end.
  • Demo recorder with a real screen. Verified end to end with a simulated screen source; a first capture in Chrome or Edge is still to do.
  • Platform sign-in. In production the hosting platform signs users in; its role claim must be matched to admin (chapter 3).
  • CI and frontend tests. Backend tests run locally; there is no CI workflow and no frontend test suite yet.
  • Team sharing. Only individual users today; the schema is ready for teams.
  • DNS rebinding. The private-address check runs at save and test, not on every connection.
  • Cold-query throughput. One job per prefork worker process; more processes or an asyncio-native worker would raise the ~280 cards/s cold ceiling measured on a laptop.
  • Pre-aggregations. Designed (rollups at the grain of a dashboard's filters) but not built; this is the answer for very large, slow sources.
  • Assistant and card overrides. The assistant sees cards with the dashboard-level filters, not per-card overrides.
  • Demo dates. Period presets end on 11 June 2026 to match the sample data.

Glossary

Asset
A card, dashboard or data source as a stable identity, independent of its versions.
Version
An immutable snapshot of an asset's name, description and spec.
Head
An asset's current version.
Pin
A reference to an exact version (a dashboard placement to a card version, a card to a source version).
Scope
Private (an owner's workspace) or global (the shared library).
Copy / fork
A private copy of a global asset that remembers which global version it came from.
Change request
A proposal to publish new assets or update global ones, reviewed by an admin.
Bundle
The asset plus its private dependencies, submitted and approved together.
Base
The global version a copy was made from; one of the three inputs to a merge.
Semantic model
A source's business vocabulary: datasets, dimensions, measures, time dimension.
Semantic query
A card query in business terms, compiled to SQL per source dialect.
Applied / ignored
Which requested filters a card's source could and couldn't bind.
Extract
A DuckDB copy of REST or file data that cards query.
Single-flight
Making concurrent requests for the same result share one computation.
Stale-while-revalidate
Serving an expired cached result immediately while refreshing it in the background.
Source slot
One of a source endpoint's limited concurrent query permits, shared across all workers.
Circuit breaker
Pausing a failing source briefly so it can recover and workers aren't tied up.
Storage key
A write-once name for a stored file, such as files/12.duckdb, resolved to local disk or S3.
Job deadline
The hard limit on one card run: the source's timeout plus 10 seconds.
Worker progress
The time a worker last finished or discarded a task; the basis of the stuck-worker check.
Reel
The self-contained HTML walkthrough the demo recorder exports.
