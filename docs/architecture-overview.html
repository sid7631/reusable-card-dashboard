SpendBoard Architecture

How the governed card-and-dashboard platform is built: who talks to whom, how every card, dashboard and data source is versioned and published, how filters bind across sources, how queries run at scale and survive a hung source, where files live, how the platform reports its own health, and how the dashboard assistant answers without seeing raw data.

System

Four deployable pieces: a Node web server (the SPA plus, in development, a simulated identity provider), a stateless FastAPI service that can run as many replicas, Celery workers that run every card query, and Celery beat for scheduled work. Postgres holds only metadata; Redis is the result cache, the lock service and, by default, the job queue; uploaded files and DuckDB extracts live on a shared disk or in S3. No API request ever queries a data source directly.

Sign-in

The web server plays the identity provider. Picking an account on the sign-in page calls POST /auth/token, which returns an RS256 JWT (sub, email, name, roles, iss, aud, exp — one hour). The SPA keeps it in sessionStorage and sends it as Authorization: Bearer on every API call. FastAPI verifies the signature against the cached JWKS, checks issuer, audience and expiry, and creates the user row on first sight (just-in-time provisioning). The role comes from the token's roles claim; demo users are Avery (admin), Riley and Jordan (users). A seed step pre-creates them so they can be found for sharing before first sign-in.

In production the hosting platform signs users in. Connecting to it is configuration: point JWKS_URL, JWT_ISSUER and JWT_AUDIENCE at the platform, and check its token marks admins with "admin" in a roles list (backend/app/core/auth.py) — a different claim name is a one-line change.

Versioning

Cards, dashboards and data sources share one model. An asset is the stable identity (kind, owner, scope, lineage, current head). Every save appends an asset version holding the full typed spec. Versions are never updated or deleted — a database trigger rejects it — so "restore v3" appends a new version with v3's content. References between assets name a specific version, which makes every version a complete, reproducible snapshot.

Spec per kind

  • Data source: type, connection / REST / file settings, execution policy (concurrency, timeout, cache TTL), semantic model.
  • Card: chart type, pinned data-source version, query (raw SQL or semantic), builder and display config.
  • Dashboard: placements (stable item_id, pinned card version, layout) and filter definitions.

History screens

  • Version list with author, time and change note.
  • Structural diff per JSON path; SQL shown as a line diff; dashboard placements labelled by card name.
  • Restore appends a new version; viewers can browse but not restore.

Publishing

Analysts never edit global assets in place. Edit a copy creates (or reopens) a private fork that remembers which global version it came from. From there the user proposes changes; a new private asset is requested for publish. Both create a change request that an admin approves or rejects. Admins may also edit global assets directly; that is a new version and an audit event.

RuleBehaviour
BundlingPrivate dependencies are included automatically, dependencies first (source → card → dashboard). Someone else's private asset can't be bundled — its owner publishes it first.
One open request per assetA second submit is refused; instead the requester pushes newer saves into the open request (Update to my latest versions).
Review screenPer item: changes vs the global base, live preview of proposed cards, staleness ("global is now v5"), conflicts.
ApproveOne transaction: each item becomes a new global asset or a new global version; references to private assets are rewritten to the new global versions; unchanged copies reuse the existing version; the requester is the version's author and the admin the approver.
Reject / withdrawReject needs a comment; only the requester can withdraw. Both return the user to their private copy.
BadgeSidebar shows pending count — the whole queue for admins, own requests for users.

Merging

When global has moved since the copy was made, a request merges like a pull request. Specs are JSON, so the merge is three-way and per path: dashboard placements are matched by item_id, filters by id, model entries by name, and multi-line text (SQL) by line hunks.

SituationResult
Global unchanged since the forkfast-forward the copy becomes the next global version
Both changed, different paths (e.g. admin edits description, user edits SQL)auto-merged both changes land
Both changed the same SQL, different linesauto-merged line hunks combine
Same path changed differently, or deleted on one side and edited on the otherconflict resolve via Update from global

A viewer of a dashboard can render the card versions it pins without access to the cards themselves, and use the assistant on it. Results are the same for every user (no row-level security), which is why cached results can be shared.

Data sources

Every source sits behind one connector interface (execute, test, introspect), so cards, filters and the assistant don't care what kind it is. Onboarding is: pick a type → connect or upload → Test connection → edit the suggested semantic model → save as a private source → request publish.

TypeHow it's queriedDetails
PostgresIn place, SQL pushed downPooled asyncpg; read-only transaction; statement_timeout; server-side cursor stops at 1,000 rows; pool size = per-process concurrency cap
BigQueryIn place, SQL pushed downService-account key or (admins) the server's identity; typed @p parameters; maximum_bytes_billed per source (default 10 GB) fails a costly scan before it runs; job timeout + cancel; API retries capped at the source timeout
REST APIFetched into a DuckDB extract, re-fetched after the cache TTLBearer / API-key header / basic auth; page-number pagination; dot path to the records; nested objects flattened; no redirects; 20 MB and 100k-record caps; each refresh writes a new extract and moves a Redis pointer, once across the cluster
CSV · Excel · JSONIngested once into a DuckDB database50 MB uploads; every Excel sheet becomes a table; mixed-type columns fall back to text; only the uploader can build sources from a file; stored under keys like files/12.duckdb

DuckDB databases are opened read-only with external access disabled and configuration locked, so user SQL can only see that source's tables — no file reads, exports, ATTACH or extension installs, verified under concurrent load.

Each source sets its query timeout in its editor: 30 seconds by default, up to 5 minutes for slow warehouses. QUERY_TIMEOUT_S (default 300) is only the server-wide ceiling.

Semantic layer

Each data-source version carries a semantic model: datasets (tables) with business labels and descriptions, dimensions (name → column, type), measures (aggregate expressions such as SUM(amount), labelled "Total spend"), and a time dimension. Testing a connection proposes a model from the table's columns; the owner edits roles, labels and descriptions. The same model drives the card builder, filter binding and the assistant.

Semantic cards

The builder saves a card as a query in business terms — dataset, measures (model measures or an ad-hoc aggregate), up to two dimensions with time grains (day → year), static filters, sort, limit. The server compiles it to Postgres, DuckDB or BigQuery SQL per request, through one dialect module (quoting, parameters, list membership, date grains). Model measure expressions are parsed and must be plain aggregates; the final SQL passes the same read-only validator as hand-written SQL.

Raw-SQL cards

Still supported for power users. SQLGlot parses the text and allows exactly one read-only query. A {{filters}} marker is replaced with conditions bound as $1, $2… parameters (typed @p1… on BigQuery), never pasted into the SQL. "View SQL" on a semantic card shows the same editable form: static filters as quoted literals plus the {{filters}} marker.

dataset   transactions          measures   total_spend  = SUM(amount)      "Total spend"
time      txn_date                         txn_count    = COUNT(*)         "Transactions"
dims      segment, sub_segment,            avg_ticket   = AVG(amount)      "Average ticket"

Filters

A dashboard defines its filters: a dimension, single or multi select, an optional parent, a lock, a default, plus an optional period filter. Filters are expressed in business terms; each card binds them through its own source's model.

Cascading

A child filter's options are the dimension's distinct values narrowed by every ancestor's selection (GCS → G&L, MM, SBS). Changing a parent clears its descendants. Options are cached for five minutes per source version and selection.

Override levels

Effective value per card = the card's own dropdown (if the card exposes that dimension and the dashboard filter is not locked) → the dashboard selection → the default → no filter. Card overrides reset when the dashboard filters change.

Execution at scale

A dashboard loads in one request: POST /dashboards/:id/render with each card's effective filters, answered as a server-sent-event stream — cached cards first, the rest as workers finish. Each card shows "as of HH:MM".

Why the deadlines exist

On 5 October 2026 a BigQuery endpoint became unreachable. The Google client library retries failed calls for up to ten minutes by default (and wraps job inserts in its own ten-minute retry), so every worker process sat retrying. Cards on every other source then queued behind them and timed out after 60 seconds, and the backlog grew to 272 jobs. Now every BigQuery call retries only within the source's timeout, each job has a hard deadline, queued jobs expire, and the circuit breaker sees the failures and pauses the source.

The job queue is swappable

Work reaches a queue in one place, backend/app/execution/queue.py (submit and handle); caching, locks and result delivery don't depend on it. CELERY_BROKER_URL moves the queue to RabbitMQ or SQS without code changes. Kafka was assessed and rejected for this job queue: work is pinned to partitions, so a slow query blocks those behind it, and it has no per-job retries or priorities. It would fit alongside as an event stream (for example "version published", "request approved").

File storage

Uploaded files and DuckDB extracts go through one interface, backend/app/core/storage.py. Code and the database hold keys, never paths, so switching from a shared disk to S3 is configuration only. Keys are write-once — a new version of something is a new key — so a worker's cached copy of an S3 object can never be stale.

WhatKeyLifecycle
Uploaded fileuploads/<id>.<ext>Written once at upload; kept
Its DuckDB databasefiles/<id>.duckdbBuilt in scratch space, then stored; never changes
REST extractrest/<version>-<config hash>/<ms>.duckdbEach refresh is a new key; a Redis pointer names the current one; refreshed by one process at a time (Redis lock); the previous extract is kept, older ones deleted

Switching an install to S3: migration 0004 already rewrote older absolute paths to keys; copy the uploads/ and files/ folders into the bucket; set STORAGE_BACKEND=s3 and the S3_* settings. REST extracts rebuild themselves.

Health and monitoring

A running API doesn't mean dashboards work: workers can be alive yet stuck, and then every uncached card fails while process checks stay green. Health is therefore measured by progress. Every worker records each task it finishes or discards; backend/app/ops/health.py compares that with the queue.

The probe endpoints sit outside /api, so the web server never exposes them publicly. Suggested alert: spendboard_status == 2 for two minutes.

Dashboard assistant

A floating chat button on every dashboard. Questions are answered from the cards as currently shown — the same filters and the same cached results — with the cards cited ("From …", click to jump) and filter buttons ("Filter to GCS →") that apply a dashboard filter only when clicked.

offline defaultLLM_PROVIDER=offline — no model calls; answers totals, leaders, growth, top N, concentration and overview from the figures on screen
openai Ollama / OpenAILLM_PROVIDER=openai · LLM_BASE_URL=http://localhost:11434/v1 · LLM_MODEL=<model>
azure Azure OpenAILLM_PROVIDER=azure · AZURE_OPENAI_ENDPOINT · LLM_API_KEY · LLM_MODEL=<deployment> · AZURE_OPENAI_API_VERSION
  • At most 6 tool rounds, then the model must answer; <think> blocks from local models are stripped.
  • Card names, descriptions and tool results are given to the model as data; the system prompt says instructions inside them are text.
  • 20 questions per user per minute; each question is audited (length, tools used). Answers aren't stored.
  • Model errors (unreachable, auth, missing deployment, rate limit) come back as a clear 503 message.

Frontend

Server data

Lists, details, versions, shares, requests and filter options come through TanStack Query (lib/queries.ts): cached, shared between components, de-duplicated. Every successful write marks governance data stale, so lists, the approvals badge and "update available" refresh on their own. Card results and filter values are keyed by immutable versions and never invalidated by writes.

Editing state

The dashboard page keeps its layout and the viewer's filters in a reducer (lib/dashboardEditor.ts); background refreshes never overwrite unsaved layout edits or reset filters. The card and data-source editors fill their forms once per version, so a refetch can't wipe edits in progress.

Demo recorder

Record demo in the sidebar captures a guided walkthrough and exports it as one self-contained HTML reel. It lives in apps/web/src/features/demo-recorder/, loads only when used, and is removed by deleting that folder and two lines in App.tsx (or switched off with VITE_DEMO_RECORDER=false).

Open items

These are known limits of the current build, not bugs found in testing.
  • Assistant not yet run against a real model. Tested with a scripted OpenAI-compatible server; configure Ollama or Azure to try it.
  • Demo recorder's first real capture. Verified end to end with a simulated screen source; a first run in Chrome or Edge is still to do.
  • Platform sign-in. Production sign-in comes from the hosting platform; its role claim must be matched to admin.
  • CI and frontend tests. Backend tests run locally; there is no CI workflow and no frontend test suite yet.
  • Team sharing. The share table already has a grantee type; only users are supported.
  • DNS rebinding. The private-address check runs when a source is saved or tested, not on every connection.
  • Cold-query throughput. Prefork workers run one job per process; an asyncio-native worker or more processes would lift the ~280 card/s cold ceiling.
  • Pre-aggregations. Designed but not built — rollups for global dashboards so filter changes on huge sources hit a summary table.
  • Assistant scope. Card-level filter overrides aren't sent with the question; the assistant sees each card with the dashboard-level filters.
  • Demo period presets end on 11 June 2026 to match the sample data.
